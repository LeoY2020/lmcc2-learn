    第 29 章 与编程 Agent 协作的方法¶

    本章目标

    学完这一章，你能：① 把八条要求排成一张有先后、可验收的任务队列；② 用「操作 → 预期」的句式写出 Agent 一听就懂的指令；③ 用官方那个 A、B、C、D 的例子检验移动功能；④ 让 Agent 自查而不是自己动手；⑤ 背下六条禁止事项。

    前两章把「要做什么」讲完了，这一章讲「怎么让 Agent 真正做到」。这里有一个观念要先转过来：跟 Agent 对话不是聊天，是下发工单。合格的工单有三个特征：说的是可观察的行为，给出的是可复现的验收步骤，一次只包含一件事。

    29.1　一次只改一件事：把八条要求排成任务队列¶

    为什么强调「一次只改一件事」？三个很现实的原因：① 出错定位快（一条指令塞五件事，改完不对你不知道是哪件引起的）；② 验收标准清楚（一件事对应一组「操作 → 预期」，你一眼就能核对）；③ 省 Token（Agent 改得少、输出短，不用因为「又改坏了」而整轮重来）。

    下面是一条推荐的开工顺序，把八条要求拆成 9 条工单。顺序遵循一个原则：先做能立刻看见效果的基础功能，再做依赖它们的边界规则，最后做持久化和整齐化。 抄在纸上，每完成一条打个勾。

    # 工单 对应要求 做完后怎么验收
    T1 数据结构与渲染基线：每条作业用唯一 data-id，标题放 label，全清单数组渲染成 .todo-list 里的 li；保留所有既有选择器 要求 1、5（基础） 添加三条、删除一条、勾选一条，功能都正常
    T2 行内科目下拉框（select.task-subject）：显示当前科目，改它只改这一条 要求 2、3 改第 2 行科目，第 1 行与同名另一条都不变
    T3 顶部科目筛选（select#subject-filter）：all / unassigned / chinese / math / english 要求 4 切「数学」只显示数学作业，切回全部顺序不变
    T4 顶部科目筛选与完成筛选联合生效 要求 4 「数学 + 未完成」只显示未完成的数学作业
    T5 上移 / 下移：只与当前可见的相邻项交换，交换的是全清单位置 要求 5 用 A、B、C、D 例子核对全清单顺序
    T6 按钮边界：可见第一条上移禁用、最后一条下移禁用、只剩一条都禁用；用原生 disabled 要求 6 每步操作后检查每条可见行的两个按钮
    T7 刷新持久化：整份全清单写入 localStorage，加载时读回并渲染 要求 7 刷新后标题、完成、科目、顺序都在
    T8 新作业规则复核：未分类、未完成、追加末尾，空标题不加 要求 2、1 在数学视图下添加，切回全部看它在末尾且为未分类
    T9 清理核对：剩余数看全清单、清理已完成删全清单已完成条目 要求 1 在筛选视图下点清理，切回全部看结果

    这张队列还有个隐藏好处：T1 必须最先做，因为它是所有功能的地基；T7 放在比较靠后，因为它依赖数据已经有 subject 字段，科目功能没做之前做持久化会白做一遍。

    技巧

    第一次对话建议把「不许动的东西」和「第一件要做的事」合并成一条消息，一轮就立好地基和护栏：「请先不要改功能，只做一件事：确认每条作业有唯一 data-id、标题在行内 label 中、并且 .todo-list 的直接子元素就是 li。另外请保留 .new-todo、.toggle、.destroy、.clear-completed、.todo-count strong、.filters a 这些既有选择器，不要改名，也不要增加中间层。」

    29.2　用「操作 → 预期」的句式下指令¶

    Agent 不看你脑子里的画面，它只看你打出来的字。最有效的指令句式是固定的三拍：① 前提（在什么状态下）→ ② 操作（点哪、改什么、选什么）→ ③ 预期（页面上应该出现什么）。缺了第三拍，Agent 就只能靠猜。下面这八条可以直接抄进对话框（按需改写标题和科目）。

    指令 1：行内科目只改这一条¶

    请实现行内科目下拉框 select.task-subject。
操作：输入「朗读」按 Enter，再输入一次「朗读」按 Enter，出现两条同名作业；
把第 2 行的科目改成数学。
预期：两条作业仍然存在，第 1 行科目仍是未分类，第 2 行变成数学；
标题、完成状态、两条在全清单里的顺序都不变。

    关键在「两条同名作业」这个前提。它逼着 Agent 用 data-id 定位，而不是用标题定位，把最容易踩的坑提前摆到台面上。

    指令 2：新作业一律未分类¶

    请确认新作业的默认值。
操作：把顶部科目筛选设为「数学」，然后输入「听写」按 Enter。
预期：当前视图里不出现「听写」（因为它是不符合筛选的未分类）；
把科目筛选切回「全部科目」后，「听写」出现在全清单末尾，科目为未分类、未完成。

    注意它把「看不见」也写成了预期。这正是要求二的难点：新作业不会因为你在看数学就变成数学。把「看不见」写进预期，Agent 才不会自作聪明地替你归成数学。

    指令 3：联合筛选同时生效¶

    请让科目筛选与完成筛选同时生效。
操作：添加「预习语文」「数学订正」「英语阅读」三条，
把第 1 条设为数学、第 2 条设为英语、第 3 条设为数学，再勾选第 2 条。
预期：科目选「数学」时只显示「预习语文」和「英语阅读」两条；
此时再把完成筛选设为「已完成」，视图应为空（数学里没有已完成的）；
把完成筛选改回「全部」，两条数学作业重新出现，且顺序不变。

    这条指令故意让「数学 + 已完成」的结果为空。空列表最容易被忽略，用一条预期把它提前暴露出来，省掉后面很多轮返工。

    指令 4：移动只与当前可见的相邻项交换¶

    请实现上移 / 下移，注意交换的是全清单里的位置。
操作：添加 A、B、C、D 四条，把 A 设为数学、B 设为英语、C 设为数学、D 保持未分类；
科目筛选选「数学」（可见 A、C），点 C 的上移。
预期：数学视图变成 C、A；把科目筛选切回「全部科目」，全清单应变成 C、B、A、D。
也就是 B 和 D 的位置一动不动，A 和 C 互换。

    这条就是题面给的官方例子。它同时给出中间状态（数学视图）和最终状态（全清单）两种预期，让 Agent 没有含糊的空间。

    指令 5：边界按钮用原生 disabled¶

    请实现移动按钮的边界禁用。
操作：添加「第一项」「第二项」「第三项」三条。
预期：第 1 行的上移按钮是 disabled，第 3 行的下移按钮是 disabled，
第 2 行两个按钮都可用；删除到只剩一条时，这一条的两个按钮都 disabled。
要求：用按钮的 disabled 属性，不要只是变灰；禁用时按钮仍然显示在行内。

    最后一句非常重要。「变灰」和「disabled」不是一回事。把要求写进指令，等于提前堵住这个错。

    指令 6：任何改变可见集合的操作后都重算按钮状态¶

    请检查按钮状态是否每次都会重算。
操作：添加三条作业，然后删除第 2 条。
预期：剩下的两条里，新的最后一条（原来的第 3 条）下移按钮变成 disabled；
再切换一次科目筛选，可见行的第一条上移 disabled、最后一条下移 disabled。

    这条专门给「只在初始化时算一次」这种错准备：它把「删除之后」和「切换筛选之后」两个时机都点出来，逼 Agent 把重算写进渲染流程。

    指令 7：刷新持久化¶

    请用 localStorage 实现刷新恢复，只存整份全清单。
操作：添加「代数」（设为数学）、「听写」（未分类）、「课文」（设为英语）三条，
勾选「听写」，然后把「课文」上移一次；刷新页面。
预期：刷新后三条的顺序、科目、完成状态与刷新前完全一致，条数不多不少；
再添加一条「新作业」，它应出现在全清单最后且为未分类。
要求：不使用网络，不保存筛选状态也没关系（恢复为全部即可）。

    「条数不多不少」这句专门防「刷新后条目翻倍」。最后一句主动说明「不保存筛选也没关系」，避免 Agent 花时间去持久化不必要的东西。

    指令 8：剩余数与清理看全清单¶

    请确认剩余数和清理都基于全清单。
操作：添加「预习语文」（数学）、「数学订正」（英语）、「英语阅读」（数学），勾选「数学订正」。
预期：无论科目筛选和完成筛选怎么切，剩余数始终显示 2；
在「数学」筛选下点击「清理已完成」，切回全部科目后，被删掉的是全清单里已完成的「数学订正」，
并且当前筛选下的可见作业不受影响。

    「无论怎么切」这个措辞把剩余数与筛选无关讲透了，同时又明确了清理的删除集合是「全清单里的已完成条目」，还把 P02-1 第 12 步那种「筛选视图下点清理」的场景提前验一遍。

    技巧

    八条指令有一个共同结构：前提 → 操作 → 预期。临场造新指令时照这个壳子填就行。拿不准写什么预期，就回到第 37 章那张速查表，抄一条公开点的预期文字，改写成你的数据。

    • 先跑通基础功能，再处理边界 —— 具体怎么排，见 19.5。
    • 让 Agent 自查，而不是自己动手 —— 具体怎么问，见 19.4。
    • 用例子纠正 —— 具体怎么举，见 19.3。

    29.3　用例子纠正：从 A、B、C、D 学会「交换的是全清单位置」¶

    跟 Agent 沟通时，例子比形容词有用一百倍。你说「移动逻辑不对」，Agent 只能猜；你说「点 C 的上移后，全清单应该变成 C、B、A、D，可现在不是」，Agent 立刻知道差在哪。题面给的那个例子，就是本题最重要的一块「标准试纸」。

    先把官方原文的例子完整摆一遍，每一步都写出理由：

    起始全清单：A（数学）、B（英语）、C（数学）、D（未分类）

第 1 步：科目筛选选「数学」
  可见的是：A、C（B 是英语、D 是未分类，都不匹配）

第 2 步：点 C 的「上移」
  要找的对象 = C 在数学视图里的上一条 = A
  要做的动作 = 把 A 和 C 在「全清单」里的位置互换
  数学视图变成：C、A
  全清单变成：C（数学）、B（英语）、A（数学）、D（未分类）
  注意 B 和 D 的位置没变（还是第 2、第 4 位）

第 3 步：再点一次 C 的「上移」
  预期：没有变化，因为 C 已经是数学视图的第一条，上移按钮应当 disabled

第 4 步：把当前可见的 C 改成英语
  数学视图变成：只剩 A
  全清单顺序不变：C（英语）、B（英语）、A（数学）、D（未分类）

第 5 步：科目筛选切回「全部科目」
  可见的是：C、B、A、D（顺序和第 2 步结束时一致）

第 6 步：刷新页面
  科目与这个顺序仍在（持久化生效）

    请注意第 2 步里那句「数学视图变成 C、A」和「全清单变成 C、B、A、D」要同时成立。这两句话合起来才唯一确定了「怎么交换」。如果只检查数学视图，一个错误实现（在可见列表内部交换）也能蒙对。 所以验收时必须多走一步：切回「全部科目」再看一遍。

    第 4 步还揭示了另一条容易忽略的规则：把 C 改成英语后，它在全清单里的位置保持不变，只是不再符合「数学」筛选，所以从当前视图消失。很多人把「消失」误解成「移走」，那就错了。

    发现 Agent 做错了，最高效的纠正是把「预期」和「实际」并排写出来，再附上你观察到的路径。可以直接套这个模板：

    我按你的实现试了一遍，结果不对，请按下面对照检查：

操作：添加 A、B、C、D 四条；A 设为数学，B 设为英语，C 设为数学，D 保持未分类；
科目筛选选「数学」（此时可见 A、C），点击 C 的上移。

预期：数学视图变成 C、A；切回「全部科目」后全清单是 C、B、A、D。
实际：数学视图变成了 C、A，但切回「全部科目」后全清单顺序不对。

请检查 move-up 是不是把「可见列表里的相邻两条」在全清单里的下标做了交换，
而不是只动了显示顺序；B 和 D 在全清单里的下标应该始终不变。

    这条模板有三段：操作、预期、实际，最后附上你的猜测。附猜测这一步很关键——它不是让 Agent 照抄你的想法，而是把讨论迅速聚焦到嫌疑最大的那段逻辑上，省下它从头读一遍代码的 Token。

    考试怎么考

    公开点 P04-1 用的就是「隐藏条目夹在中间」的结构（计算A、英语B、计算C、未分D、计算E）。它的第 11～13 步连续三次移动，每一步之后都核对「所有移动按钮符合可见列表边界规则」，第 14 步再切回「全部科目」核对全清单。这说明平台判断移动的正确性，是可见顺序与全清单顺序一起看的。

    坑

    用例子纠正时，别只说「顺序不对」。顺序不对有很多种可能：移动逻辑错了、渲染顺序错了、或者筛选时顺手重排了数组。把「预期顺序」和「实际顺序」都完整写出来（把四个字母都列出来），才能让差异自己说话。

    29.4　让 Agent 自查，而不是自己动手¶

    考试不许你动手改代码，所以「检查」也必须交给 Agent——但要检查得好，问法很重要。笼统地问「有没有问题」等于没问；把要检查的规则和要检查的位置一起说出来，才有效。下面六种问法可以直接抄。

    # 可以直接抄的自查指令 它在防什么
    1 请检查 move-up 是否与当前可见的上一条交换，而不是与全清单里的上一条交换；并说明交换时是否连 data-id 一起换了位置。 移动对象搞错；只交换标题不交换整条数据
    2 请检查按钮的 disabled 是否每次渲染都按当前可见顺序重算，包括删除、勾选、改科目、切换筛选之后。 只在初始化时算一次，之后不更新
    3 请检查剩余数 .todo-count strong 是否只统计全清单中未完成的条目，与当前筛选无关。 把剩余数算成可见未完成数
    4 请检查保存的字段是否包含 id、title、subject、completed，并且按全清单顺序整体写入 localStorage；加载时是否只有一处读取并渲染。 漏字段；恢复与内存双份导致条目翻倍
    5 请检查行内科目下拉框的修改是否只更新 data-id 对应的那一条，改完后重新渲染并重算按钮状态。 只改显示不改数据；影响同名条目
    6 请检查 .todo-list 的直接子元素是否就是每条作业的 li、每行是否有唯一 data-id、标题是否在行内 label 中。 加包装层导致平台找不到可见行

    这些问法的共同点：把规则原文（「与当前可见的上一条交换」「与筛选无关」「只更新对应那一条」）直接嵌进问题里。Agent 必须逐条对照，而不能含糊地回答「已检查，没问题」。

    Agent 会告诉你它改了什么、检查了什么，但它的自述不能当作最终结论。你仍然要回到页面预览里走一遍例子。判断报告可信度有个小技巧：看它有没有提到具体的函数名或文件。

    含糊不可信：
  「已修复移动逻辑，现在符合要求。」

具体可用：
  「已修改 src/app.js 里的 moveUp / moveDown 两个函数：
   先用 computeVisible() 取当前可见数组，再用 indexOfId() 找到本条与相邻条在全清单里的下标，
   用 swapInFullList() 交换这两个下标；交换的是完整的任务对象（含 id、title、subject、completed）。
   同时 render() 里新增了按可见序号设置 disabled 的循环。」

    第二种报告之所以可信，是因为它暴露了实现细节，你一看就知道它是不是按规则做的。反过来，如果 Agent 只说「已修复」「已按你的要求处理」，你就必须自己再验一遍。

    技巧

    还有一个省钱的问法：「请只回答两个问题：① move-up 是在全清单数组上交换下标，还是在可见数组上交换？② 边界 disabled 是在 render 里统一设置的吗？不要贴完整代码。」 这种限定式提问能拿到关键信息，又不会让 Agent 输出一大段代码占用 Token。

    坑

    不要问「你觉得还有哪里有问题」这种开放问题。Agent 很可能为了显得负责，主动去改一些没坏的地方，甚至重写整个文件——既费 Token 又可能引入新错误。要问就问具体的、封闭的、有明确答案的问题。

    29.5　迭代纪律：先跑通基础功能，再处理边界¶

    40 分钟听着不少，但对话是有来回的：你打一句、Agent 读代码改代码跑命令、再回你一句，一轮通常 1～3 分钟。算下来你大概只有 15～25 次真正有意义的交互。所以顺序比完美更重要。 纪律的核心是一句话：先把「主流程能跑」这条线打通，再加边界；不要为了一个边界卡住整条主流程。 主流程就是「添加 → 显示 → 改科目 → 筛选 → 移动 → 刷新后还在」这一整条链。

    阶段 目标 判断能不能进入下一阶段
    第 1 阶段：地基 每条作业有唯一 data-id、标题在行内 label 里、.todo-list 的直接子元素是 li 添加三条、删除一条、勾选一条都正常
    第 2 阶段：科目与筛选 行内科目可用；顶部科目筛选与完成筛选同时生效 「数学 + 未完成」结果正确，切回全部顺序不变
    第 3 阶段：移动 上移下移按「当前可见的相邻项」交换全清单位置 A、B、C、D 例子在数学视图与全清单两边都对
    第 4 阶段：边界 按钮边界、空列表、只剩一条、同名条目 P03-2 那种逐步检查全部通过
    第 5 阶段：持久化 刷新后标题、完成、科目、顺序都在 刷新一次再添加一条，条数不多不少
    第 6 阶段：整体复核 按第 37 章那张速查表过一遍八条要求 每一条都能说出「我怎么验过它」

    每个阶段结束，都要在预览里按「操作 → 预期」走一遍。走通了再进下一阶段；走不通就先修这一个问题。绝对不要在没有验证第 2 阶段的情况下直接跳到第 5 阶段，因为后面的功能全都建立在前面的数据结构上，地基错了，上面全得返工。

    下面这张表就是「第 4 阶段」要逐条确认的东西，当成一张打卡清单用：

    边界情况 怎么造出来 预期
    空标题 输入三个空格再按 Enter 清单不变，不新增条目
    首尾空白 输入两个空格 + 「数学练习」+ 两个空格 标题存成「数学练习」，中间空格保留
    同名条目 同一个标题输入两次 两条独立；改一条的科目、勾选不影响另一条
    可见列表为空 先切「已完成」再看 页面没有行，但科目筛选仍可用
    只剩一条 添加两条后删掉一条 这一条的上移和下移都 disabled
    第一条 / 最后一条 三条可见时检查 第 0 条上移 disabled、最后一条下移 disabled，中间两个都可用
    切换筛选后的边界 切一次科目筛选再检查按钮 按新的可见顺序重算，边界正确
    改科目后消失 在「数学」筛选下把唯一一条改成英语 可见列表为空，且全清单里它还在
    筛选视图下清理 筛到只剩一条未完成，点「清理已完成」 被删的是全清单里已完成的条目，不只是可见的
    刷新后追加 刷新后再添加一条 追加到末尾，条数 = 原有 + 1，不重复

    这张清单里，前四条属于「要求一」和「要求二」，中间四条属于「要求六」，后两条在公开点 P02、P05 里各出现过一次。它们全都出现在公开点上，所以这不是「锦上添花的优化」，而是「必须拿到的分」。

    如果时间真的不够，取舍要有依据。判断依据是谁的分更容易拿到：① 优先保地基与筛选（要求 1～4 覆盖 P01、P02、P03 的大部分步骤，是最粗的柱子）；② 其次保移动主流程（P04、P05 都围绕移动）；③ 再保边界（边界禁用、空列表、只剩一条，常常是一个点是否拿满的决定因素）；④ 最后保持久化（实现简单、性价比高，一般不该砍）。

    考试怎么考

    从分值结构看：一个点 10 分、两个子场景全部通过才给分。所以时间紧张时，「让一个点彻底通」比「三个点各差一步」更划算。你在预览里验收时，也应该按「一个点走到底」的方式走，而不是每个功能都碰一下。

    29.6　禁止事项：六件绝对不能做的事¶

    这一节是本部分的「红线清单」。每一条都有明确的理由，违反它们轻则浪费 Token，重则直接丢分。

    禁区一：不要让 Agent 重写整个项目¶

    「帮我把这个项目重写一遍」是最贵的一句话。它会烧掉大量 Token，还会把已经正确的原功能（添加、勾选、删除、清理）一起推倒重来——而平台正在用这些原功能给你打分。更糟的是，重写之后选择器和结构都可能变化，平台可能定位不到控件。要求增量修改，一次只动一个文件或一个函数。

    不要：「这个项目太乱了，你重构一下吧，把管理逻辑都重写。」
而要：「只改 src/app.js 里的 moveUp 和 moveDown 两个函数，其它文件不要动；
       修改后请说明你动了哪几行。」

    禁区二：不要改题面、测试和启动脚本¶

    题面写明：「题面、来源说明、许可证、启动脚本及测试内容固定。」这些东西是平台验收的依据。你唯一可以动的是 index.html、src/、assets/，或者在 src/ 与 assets/ 里新增源码和样式文件。如果 Agent 提议「我改一下测试就能过」，必须立刻制止。

    禁区三：不要联网¶

    「工作区不能联网」是硬条件。任何需要联网的方案（下载库、请求接口、CDN 资源）都会失败或不合规。这也是为什么持久化必须用浏览器本地存储。第一次对话就把「不要联网、不要下载任何依赖」说清楚。

    禁区四：不要用「贴长日志」的方式沟通¶

    把几百行运行日志整段贴进对话框，会让下一轮的输入变得非常大，而且日志里大部分内容跟问题无关。只贴关键几行，并说明「这是在点 C 上移之后打印的可见顺序和全清单顺序」。

    不要：一句「我把日志贴给你，你自己找问题」后面接 300 行输出。
而要：「点 C 上移后，我让页面打印了数组：visible = [A, C]、full = [A, B, C, D]；
       说明 move-up 只改了 visible 的顺序，没有改 full 里的下标。」

    禁区五：不要要求与得分无关的功能¶

    撤销、搜索、批量操作、拖拽排序、动画、深色模式……题面写得很清楚：「没有撤销、搜索或批量操作要求。」这些功能不加分，却会引入新的错误、增加代码体积、拉长 Agent 的思考时间。把每一次对话都花在八条要求上。

    禁区六：不要在快没时间时开始「大改造」¶

    离上限只剩几分钟时，最忌讳的是「我把它整体理一遍」。正确动作是：① 用最后几次交互确认最核心的行为是好的；② 如果某个小问题改不干净，就想办法绕开它；③ 保留一个能跑通的版本，准备提交。

    坑

    还有一个容易被忽略的纪律问题：不要反复让 Agent「再确认一次」同一件事。每问一次都要重新带上完整对话历史（第 30 章会讲这件事的代价）。同一件事问一次就够，剩下的靠页面预览来验证。

    29.7　第三题的对话方法：三条官方原则的落地写法¶

    官方原则 第三题里的写法
    任务范围要明确 每条指令写清三件事：要解决的问题、可观察的验收标准、涉及哪些控件或文件（例如 select.task-subject）
    先研究、再计划、后迭代 第一条消息只让它读文件并给出改动计划（明确说"先不要改代码"），确认后再逐条实现
    检查它的工作 用页面预览核对"可见行顺序""按钮禁用状态""刷新后是否恢复"；再让它逐条自查

    29.8　可直接使用的第三题指令骨架¶

    第 1 条（只读）请阅读 index.html 与 src/，说明要实现【功能】需要改哪些文件与函数；先不要改代码。
第 2 条（一个功能）请实现【功能】。要求：当【操作】发生时，页面应【可观察的结果】。注意不要改动【不该动的东西】。
第 3 条（边界）请确保【边界条件】，例如当前可见第一条的上移按钮为原生 disabled。
第 4 条（持久化）请把【需要保存的字段】写入浏览器本地存储并在刷新后恢复，不调用外网。
第 5 条（自查）请不要改代码，逐条回答：①……②……③……

    技巧

    官方强调"只提供相关上下文"与"新任务开新对话"。在第三题里等价于：不让 Agent 读无关文件、不反复追问、把要求拆成 5～7 条指令逐条下达——既提高成功率，也直接省 Token（用量系数会乘在功能分上）。

    本章要记住的 6 件事

    • 对话不是聊天，是下发工单：一次只改一件事，把八条要求排成 T1～T9 的任务队列，先地基后边界。
    • 指令用三拍句式：「前提 → 操作 → 预期」；八条示范指令覆盖科目、联合筛选、移动、禁用、持久化、空列表。
    • 移动的标准试纸是 A（数学）、B（英语）、C（数学）、D（未分类）：点 C 上移后数学视图是 C、A，全清单是 C、B、A、D，B 和 D 不动。
    • 纠正时用「操作 / 预期 / 实际 + 一句猜测」的模板；自查时问封闭的具体问题，不问开放问题。
    • 迭代纪律：主流程打通 → 边界逐条打卡 → 持久化 → 整体复核；时间不够时优先保「一个点彻底通」。
    • 六条禁区：不重写整个项目、不改题面测试与启动脚本、不联网、不贴长日志、不做无关功能、临近结束不做大改造。
