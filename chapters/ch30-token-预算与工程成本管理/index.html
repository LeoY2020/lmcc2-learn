    第 30 章 Token 预算与工程成本管理¶

    本章目标

    学完这一章，你能：① 解释为什么「每一轮都会重复计费」；② 用 A=100,000、B=160,000、K=50% 的公式算出一个具体分数；③ 背下八条省 Token 的实操；④ 说出四条限额数字；⑤ 知道点提交之后会发生哪五件事。

    第 17 到 19 章讲的是「怎么把功能做对」，这一章讲的是「怎么在有限资源里把分数保住」。第三题的资源有三样：时间（本版 40 分钟）、请求次数（整题最多 80 次）、Token（用完 A、B 的规则就开始衰减）。它们通过两个渠道影响你的分数：功能原分 S 和用量系数。

    必背

    先记住这条式子：最终得分 = 功能原分 S × 用量系数。S 是十个测试点给你的分（满分 100），用量系数由累计 Token 决定（不超过 A 时为 1）。S=100 但 Token 花到 160,000，你只能拿 50 分。

    30.1　用量是怎么算的：为什么越聊越贵¶

    题面里有一句特别关键的话，直接抄下来：「用量包含每次请求的题面、你的消息、此前完整对话、代码与工具结果，以及模型输出。历史再次输入仍累计。」 这句话的意思是：模型没有「记忆」，它每一轮都要把整段对话从头到尾重新读一遍才能接着说话。

    用一个比喻理解：你和 Agent 的对话像一份越写越长的会议记录。你每问一次，就必须把目前整份记录复印一份递给它，它再在上面添几句。第 1 轮复印 1 页，第 10 轮要复印 10 页。 记录不会变短，只会变长，所以总用量不是按轮数线性增长的，而是越往后越贵。

    用量包含什么 为什么要算 你可以怎么控制
    题面 / 系统提示（固定开销） 每次请求都要带上 控制不了，只能减少轮数
    你的每一条消息 你是输入方 写短、写准、一条说完
    此前完整对话 模型没有记忆，必须重读 少来回、少废话、别反复重来
    代码与工具结果 Agent 读过的文件内容也在上下文里 别让它读无关文件；别贴长日志
    模型的输出 它写的解释和代码都算 要求短输出、只回答关键问题

    题面还补了几条细节，每一条都值得注意：「缓存输入照计，已计入输出的推理 Token 不重复累计。」 前半句说明：即使平台做了缓存，输入 Token 也一样算钱，别指望靠缓存省钱；后半句说明推理内容只在输出侧算一次。接下来两句更要紧：「自动运行测试本身不产生模型 Token。」（提交后跑测试是免费的），以及「继续对话、刷新界面、回滚代码或重新登录，都不重置账户用量或原截止时间。」（「重新开始」这条路不存在）。

    坑

    很多人有一个错误直觉：觉得「我又没让它输出多少字，应该不贵」。但实际上每一轮的最大成本是那一整份历史，不是它这轮输出。所以真正省 Token 的杠杆是「减少轮数」和「保持上下文干净」，而不是只盯着模型输出的字数。

    考试怎么考

    还有两个细节：「失败、重试或中断请求中已产生的用量仍计入。」 表示「让 Agent 重试一次」不是免费的；以及「平台调用前核算输入并预约最大输出；余额不足时缩小输出或停止调用。」 表示余额接近上限时，平台的保护动作是缩小输出或不再调用——一旦发生，你就等于被迫停手了。所以不要贴着上限去用。

    30.2　A、B、K 三个数与三个算例¶

    题面把用量的换算写成了一张表，数字必须原样记住。

    必背

    A = 100,000 Token；B = 160,000 Token；K = 50%（暂定）。K 表示「用量达到 B 时的系数」，也就是分数最多衰减到一半。

    累计用量 T 用量系数 含义
    T ≤ 100,000 1 保留功能原分，一分不扣
    100,000 系数 1 -> 80 × 1 = 80 分
    T = 130,000 -> 系数 0.75 -> 80 × 0.75 = 60 分
    T = 160,000 -> 系数 0.5 -> 80 × 0.5 = 40 分 
    第二个算例的推导：130,000 − 100,000 = 30,000，正好是 60,000 的一半，所以扣掉 0.5 的一半即 0.25，系数 = 1 − 0.25 = 0.75，得 60 分。**第三个算例说明：就算功能全对也拿不到一半以上。** 所以省 Token 本身就是得分策略。

再把「S 不同」的情况枚举一遍，让你对「省 Token 值多少分」有数量感：

| 功能原分 S | T = 100,000（系数 1） | T = 130,000（系数 0.75） | T = 160,000（系数 0.5） |
|---|---|---|---|
| 100（满分） | 100.00 | 75.00 | 50.00 |
| 90 | 90.00 | 67.50 | 45.00 |
| 80 | 80.00 | 60.00 | 40.00 |
| 60 | 60.00 | 45.00 | 30.00 |
| 50 | 50.00 | 37.50 | 25.00 |

这张表最该记住的是第一行：把 Token 从 100,000 花到 160,000，无论功能做得多好，都会**直接损失一半的分**。反过来看，**把 Token 压到 A 以内，是唯一一种「不用改代码也能加分」的手段**。

!!! warning "坑"
    关于「到达 B」那一行，题面写的是「停止模型调用，保留当前作品；用量系数为 50%」。注意它不是说你没分了，而是说你不能再让 Agent 改代码，只能拿现有的作品去评分，而且分数打对折。所以你该给自己设一条更早的线，比如 120,000 就开始收手复核。

!!! question "考试怎么考"
    结算细节：「最终只四舍五入一次，保留两位小数。」 不要在中间步骤自己反复四舍五入。另外 K 在题面里写的是「暂定」，它属于考试平台会公布的信息，考前再确认一次即可。

## 30.3　省 Token 的八条实操

知道公式之后，问题就变成「怎么在 100,000 Token 里把功能做完」。下面八条，每一条都对应一个具体动作。

### 第 1 条：指令写短，但要写准

短不等于含糊。**「请修好移动功能」是短而含糊，「move-up 要和当前可见的上一条在全清单里交换下标」是短而准确。** 后者一轮就能落地。省 Token 的关键不是「少说话」，而是**「一句话里包含足够信息，让 Agent 不需要再确认」**。

```text
差的三轮对话（每轮都要带上完整历史）：
  「移动功能有问题」-> 「哪部分？」-> 「上移不对」-> 「我再改改」

好的一轮对话：
  「move-up 现在改的是可见数组的顺序；请改成交换这两条在全清单数组里的下标，
    然后重新渲染并按新的可见顺序重算 disabled。」

    第 2 条：一次说清一组需求¶

    这和第 29 章「一次只改一件事」并不矛盾。正确组合是：一次说清一件「完整的事」（含操作与预期），而不是把一件事碎成好几条消息。

    第 3 条：不要让 Agent 读无关文件¶

    Agent 每次用 read_file 读进来的内容都会留在上下文里，之后每一轮都要重新算钱。所以要指定范围：「只看 src/app.js，不要读 index.html、assets 和测试目录。」 不确定它在读什么，就直接问：「你读了哪些文件？只回答文件名，不要贴内容。」

    第 4 条：不让 Agent 写长篇解释¶

    直接说「只回答关键点，不要贴完整代码」，Agent 就不会把几百行代码铺进上下文。文件已经写到磁盘上了，需要时用页面预览验证就行。「请用三句话说明你改了什么，不用贴代码」是很好用的一句。

    第 5 条：一次说清验收标准¶

    这是最省 Token 的一招。提需求时就把「操作 → 预期」写全，Agent 一次就能做对；只提需求不提验收，它很可能做一半、你验一半、再补一轮。把预期提前写进去，等于把它当成了需求的一部分。

    第 6 条：别反复重来¶

    「全删了重做」「再重写一遍看看」是最花钱的操作：既产生大量输出，又让后续每一轮都更贵。正确做法是定点修正——指出哪一段不对、应该改成什么。

    第 7 条：不要贴长日志¶

    日志要「摘」不要「贴」。只保留能说明问题的几行，并写清它是什么时候打印的、代表哪个变量。五行关键数据，胜过一次三百行的粘贴。

    第 8 条：尽快结束对话¶

    每多聊一轮，历史就再大一截。功能验收通过之后，最省 Token 的动作是停止对话，进入提交前复核。题面只按功能评分，不要在「还能不能再优化」上耗着。

    动作 省在哪里 一句话做法
    1 写短写准 减少反问轮数 一句话说清「改哪、改成什么」
    2 合并需求 减少消息条数 一件事一次说完，含验收标准
    3 限定读文件 减少上下文体积 「只看 src/app.js」
    4 限制输出 减少输出 Token 「三句话说明，不用贴代码」
    5 先给验收标准 减少返工 把「操作 → 预期」写进需求
    6 不重来 避免大块输出与重读 定点修正，指名要改的那段
    7 不贴长日志 减少上下文体积 只贴关键 3～5 行并注明来源
    8 尽早收手 减少后续轮数 验完就停，进入复核与提交

    技巧

    有一个很有用的自查习惯：每轮对话后看一眼用量记录。如果发现「我明明只问了一句话，怎么涨了这么多」，就说明上一轮 Agent 读了大量文件或输出了长代码——下一轮立刻收紧范围。用量记录是你的仪表盘，别从不看它。

    下面把「S 不同」的情况也枚举一遍，让你对「省 Token 值多少分」有数量感：

    功能原分 S T = 100,000（系数 1） T = 130,000（系数 0.75） T = 160,000（系数 0.5）
    100（满分） 100.00 75.00 50.00
    90 90.00 67.50 45.00
    80 80.00 60.00 40.00
    60 60.00 45.00 30.00
    50 50.00 37.50 25.00

    这张表最该记住的是第一行：把 Token 从 100,000 花到 160,000，无论功能做得多好，都会直接损失一半的分。反过来看，把 Token 压到 A 以内，是唯一一种「不用改代码也能加分」的手段。

    坑

    关于「到达 B」那一行，题面写的是「停止模型调用，保留当前作品；用量系数为 50%」。注意它不是说你没分了，而是说你不能再让 Agent 改代码，只能拿现有的作品去评分，而且分数打对折。所以你该给自己设一条更早的线，比如 120,000 就开始收手复核。

    考试怎么考

    结算细节：「最终只四舍五入一次，保留两位小数。」 不要在中间步骤自己反复四舍五入。另外 K 在题面里写的是「暂定」，它属于考试平台会公布的信息，考前再确认一次即可。

    30.4　时间与请求限制：四条硬数字¶

    除了 Token，题面还给了四条硬上限。它们决定了「你能敲多少次回车」。

    项目 题面写的限制 你要怎么应对
    作答时间 本版 40 分钟 按阶段分配时间，别在前 15 分钟纠缠配色和样式
    每条消息的模型请求 最多 4 次 Agent 收到你一句话，最多可以连续做 4 轮「读—改—跑」。超过就暂停等你下一句
    整题的模型请求 最多 80 次 这是全局预算，用完就停，所以要盯着它花
    单次模型输出 最多 8,192 Token 要求 Agent 别一次输出超长代码；让它分步改
    单条工具命令 最长 60 秒 如果一条命令跑超时，Agent 可能重试，白费请求与 Token

    先解释「每条学生消息最多触发 4 次模型请求」是什么意思。你打完一句话发出后，Agent 的工作方式是一环扣一环的：先想一轮（这是第 1 次模型请求），可能去读文件，拿到结果再想一轮（第 2 次），改完文件可能还想跑个命令验证（第 3 次），觉得不对再修一次（第 4 次）。这 4 次都算在整题的 80 次里。 满 4 次之后，Agent 会停下来等你再说一句话。

    那么 80 次是个什么概念？如果每条消息都吃满 4 次请求，你只有大约 20 条消息的额度。如果每条消息只激活 1～2 轮（比如你的指令一次就做对了、Agent 不需要反复试探），你就能发到三四十条。所以「指令写得准」不只省 Token，还直接省请求次数。

    阶段 建议投入 要完成的工单
    0～7 分钟 3～5 条消息 T1 地基、T2 行内科目、T3 科目筛选
    7～15 分钟 4～6 条消息 T4 联合筛选、T5 移动（含 A、B、C、D 例子核对）
    15～23 分钟 3～5 条消息 T6 按钮边界与重算
    23～31 分钟 2～4 条消息 T7 持久化、T8 新作业规则复核
    31～36 分钟 2～3 条消息 T9 清理与剩余数复核、边界清单逐条打卡
    36～40 分钟 尽量不再发消息 最后走一遍验收、确认无半成品，然后提交

    这张表不是必须严格遵守的课表，而是一个提醒：时间是会「用超」的。 很多人会在地基和样式上花掉一半时间，到第 35 分钟才想起来「移动还没做」——那就来不及了。上面这个分配把最容易得分的部分放在前面，把复核放在最后。

    坑

    有两个关于命令的坑。第一，如果 Agent 跑了一条命令超过 60 秒，平台会把它掐断；它可能再重试一次，于是你又花掉一次请求。第二，不要要求 Agent 做重活（比如全量构建、跑一大套测试），题面说了「无需手动运行测试」，你也不需要它替你跑测试。

    考试怎么考

    还有一个心理上的提醒：题面写的是「Agent 完成这一轮后暂停，你可以继续对话」。所以「Agent 停下来」是正常现象，不是出错。 它停下来时，你正好可以去看页面预览、核对刚才那一轮的效果，再决定下一句说什么。这个「看一眼再说话」的习惯，能帮你避免连发几条指令导致前面还没改完就叠上新的要求。

    30.5　提交与锁定：点下按钮之后的五件事¶

    全章的最后一节，把「提交」这个动作讲透。它是第三题的唯一终局动作，点下去了就没有回头路。

    • 停止与锁定：平台停止 Agent 和工具，锁定当前项目，并锁定同一时刻的累计用量。提交后不能继续改动作品。
    • 自动跑 5 个公开点：现场展示每个点的实际结果、预期结果及差异。公开功能分满分 50。这个动作不产生模型 Token。
    • 作品与用量随即锁定：达到时间或预算上限时也会冻结当前作品；「回滚代码或重新登录」都不重置用量或截止时间。
    • 隐藏点考后评测：另外 5 个点的输入、操作、预期和成绩在考试时完全不展示；考试结束后对同一份锁定项目统一评测，满分 50。
    • 按 10 点结算功能原分：每点 10 分，两个子场景全部通过才得 10 分；再用第 20.2 节的用量系数乘一次，四舍五入保留两位小数，就是最终得分。
    说法 正确理解
    需要自己点「运行测试」吗？ 不需要。平台在提交后自动运行，你也不用输入测试命令或修改测试内容
    隐藏点能不能提前知道分数？ 不能。考试期间完全不展示，也不反馈答案或分数。别把它当 0 分，也别据此估分
    提交后还能改吗？ 不能。平台停止 Agent 和工具，作品与用量一起锁定
    时间到了会怎样？ 冻结当前作品，按已有用法结算；所以最后一分钟不要动大手术

    既然提交不可逆，那么提交前要做一次「最后一遍验收」。下面这份清单你可以在心里过一遍，也可以在纸上划一遍。

    # 检查什么 怎么检查
    1 八条要求是否都实现 对着第 37 章那张速查表逐条自问「我怎么验过它」
    2 移动是否正确 用 A、B、C、D 例子走一遍：数学视图 C、A，全清单 C、B、A、D
    3 按钮边界是否正确 三条可见时第 0 条上移禁用、最后一条下移禁用；只剩一条时两个都禁用
    4 刷新是否恢复 刷新一次，核对顺序、科目、完成状态；再添加一条看是否追加末尾
    5 同名条目是否独立 同一标题添加两条，分别改科目和勾选，确认互不影响
    6 空列表是否正常 切到「已完成」看空视图；确认科目筛选仍可用、页面无报错
    7 有没有半成品 确认没有正在修改中的文件、没有 Agent 刚改到一半的逻辑
    8 用量是否安全 看用量记录：是否远低于 100,000；如果已经超过，考虑立刻收手提交

    第 8 条值得多说一句。如果你发现用量已经超过 100,000，那么继续聊下去就是在持续扣分。 每多用 6,000 Token，系数掉 0.05；S = 100 时那就是 5 分。此时正确的判断是：「我还能用这 6,000 Token 换回至少 5 分吗？」如果只是打磨细节，那不值得，直接提交。

    技巧

    提交前的最后一分钟，不要开始新的改造。如果非要动，只动「一个已知的具体错误」，并且改完马上在预览里验一遍。凡是「顺手把这里也理一下」的念头，在最后阶段都要按掉。

    本章要记住的 6 件事

    • 用量按「每次请求都包含完整历史」累计，越聊越贵：题面、你的消息、此前完整对话、代码与工具结果、模型输出都算；缓存输入照计；自动测试不算。
    • A = 100,000、B = 160,000、K = 50%：T ≤ A 时系数 1；A 到 B 之间系数 = 1 − 0.5 × (T − 100,000) / 60,000；到达 B 停止模型调用、作品保留、系数 0.5。S = 80 时三个算例是 80 / 60 / 40 分。
    • 省 Token 八条：写短写准、合并需求、限定读文件、限制输出、先给验收标准、不反复重来、不贴长日志、尽早收手。
    • 四条硬上限：40 分钟、每条消息最多 4 次模型请求、整题最多 80 次请求、单次输出最多 8192 Token、单条命令最长 60 秒。
    • 提交后五件事：停止并锁定、自动跑 5 个公开点、作品与用量锁定、隐藏点考后评测、按 10 点结算再乘用量系数。
    • 提交不可逆，提交前按 8 条清单走最后一遍验收；用量超过 A 之后，继续对话就是在持续扣分。
