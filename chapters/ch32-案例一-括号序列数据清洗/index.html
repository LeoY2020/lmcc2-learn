    第 32 章 案例一：括号序列数据清洗¶

    本章目标

    读完这一章，你能说清：第二题到底要你交什么、模型看到的输入长什么样、什么叫"合法序列"、输出格式精确到哪几个字符、以及 100 分是怎么拆成 20 分加 40 分加 40 分的。

    很多同学一上来就打开编辑器开始写生成脚本，结果写了两小时才发现标签标错了一批、函数返回的键名写成了别的单词。避免这种返工的唯一办法，是先花二十分钟把题面读成一张"规格表"。这一章就是帮你把这张表画出来。

    32.1　任务与输入格式："序列："加 2 至 12 个半角圆括号¶

    这一题让模型做的事只有一件：判断输入的括号序列是否合法。模型看到的每一条输入，都由两段拼成：一段固定前缀，加上括号串本身。

    序列：()()
序列：(()(()()))
序列：())(()())(

    把规则说精确：

    项目 规定
    固定前缀 中文序列：四个字符（"序列"两字加一个全角冒号），紧跟着括号串，中间没有空格
    括号种类 只允许半角圆括号 ( 与 )，不能出现方括号、花括号、全角括号、字母、数字、空格
    长度范围 括号串长度 2 至 12，也就是最少一对，最多十二个字符
    题目里出现的现象 合法与不合法混在一起，模型要能分开；长度有奇有偶

    坑

    前缀里的冒号是全角"："，而答案部分 [Valid]: 里的冒号是半角":"。这两个冒号长得像，实际是两个不同字符。写训练数据时如果把前缀里的冒号打成半角，训练数据里的输入格式就和评测时的输入格式不一致，模型会看到一种它考试时根本见不到的写法。这类错误肉眼很难发现，建议写完数据后统一用程序检查字符。

    还要注意"固定系统提示词"的存在。训练和评测时，平台会在你这条输入的前面自动加上下面这段话，它是只读内容，你不能修改：

    判断序列是否合法：从左到右任意前缀左括号数不能少于右括号，最终两者数目相等。合法只输出[Valid]: YES，否则只输出[Valid]: NO，冒号后一个半角空格，不加解释。
    提示词里的句子 它规定了什么
    判断序列是否合法 任务类型：只做二分类判定，不是改写，也不是解释
    从左到右任意前缀左括号数不能少于右括号 过程条件，也就是"账本不能变负"
    最终两者数目相等 结束条件，也就是"账本必须归零"
    合法只输出[Valid]: YES，否则只输出[Valid]: NO 两种输出必须逐字一致，别的一律不行
    冒号后一个半角空格 那一个空格是硬规定，不能多也不能少
    不加解释 不许写理由，不许先分析再回答

    把自己造的数据和这张表对照着看，你会发现一条规律：系统提示词说的规则，就是你造数据时用的规则；系统提示词说的格式，就是你写标签时的格式。三者必须一致，模型才不会被两套说法拉扯。

    这段话相当于模型在考试时拿到的"考试说明"。你在训练数据里不需要、也不能重复它——你只负责提供"输入 → 输出"这一对。理解这一点很重要：模型最终学到的行为，是"看到系统提示词里的规则 + 看到你给的输入，就吐出你给的那种答案"。如果系统提示词说 YES 长什么样，而你训练数据里写的是别的样子，模型就会精神分裂。

    考试怎么考

    推理时关闭 thinking（不让模型先写一段思考再回答）、使用确定性生成（同样输入永远给同样输出，不是随机抽签）、最多生成 128 Token。这三条一起决定了：模型必须"张口就说"，没有慢慢想的余地，也没有第二次机会。所以你要训练的是条件反射式的输出习惯，而不是"长篇推理能力"。

    32.2　合法序列的两个条件与四类不合法情况¶

    题面把"合法"写成了两个必须同时满足的条件。这两句话看起来平淡，但它们是整个第二题的地基：你的数据标签对不对，全靠这两句话判；模型能不能答对隐藏点，也全靠它有没有学到这两句话的差别。

    条件名 完整规则 人话解释
    过程条件 从左到右，任意前缀的左括号数量都不能少于右括号数量 边走边记账，账本不能变成负数。一旦出现"前面还没开括号就先来一个右括号"，立刻出局
    结束条件 整个序列的左括号和右括号数量必须相等 走到终点时账本必须正好归零，开了的括号必须全部关掉

    只有两条都满足，才是 YES。数量相等并不一定合法——题面特意强调了一句：)( 的左括号和右括号各一个，数量相等，但第一个字符就是右括号，过程条件当场失败，所以它是 NO。这正是这一题最想考你的地方。

    反过来说，不合法可以按"为什么错"分成四类。分类不是为了好看，而是因为你的训练数据必须把这四类都喂给模型，否则模型只会背下"数量相等就是合法"这个错误规律。

    不合法类型 错在哪里 例子（都会被判 NO）
    1. 未闭合 结束条件失败：左括号开多了，最后账本没归零 ( 不算（长度只有 1，会被清洗掉）、((、(()、(()(、((((
    2. 额外右括号 过程条件失败：某个前缀的右括号多于左括号 ())、())(、))、())))
    3. 数量相等但顺序错 两条都错得"刚好平衡"：总数相等，但中间某处右括号领先 )(、)()(、())(()、())()(
    4. 奇数长度 长度是奇数时左右数量不可能相等，必然失败；但失败的原因不止长度 ()(、(( 长度是偶数却未闭合、)))、()())

    技巧

    用 CSP-J 的老办法：把"合法"想成走楼梯。( 是上一步，) 是下一步。楼梯不能低于地面（过程条件），走完全程必须正好回到地面（结束条件）。"不能低于地面"就是"前缀里左括号不能少于右括号"。用这个比喻去生成反例，你会发现自己造出来的错误类型天然就是这四类，不会漏。

    为什么第三类最容易漏¶

    前两类错误"一眼看上去就不对"，你造数据时很自然会写出来。第三类——数量完全相等、只是顺序错了——才是真正的考点。)()( 这种串，如果只看"左括号几个、右括号几个"，会得出"相等，合法"的错误结论。而一个只见过合法串和明显坏串的模型，只要发现"数量相等"这条捷径就够它在训练集上拿满分了，于是在隐藏点上遇到这种平衡但顺序错的串就会答错。

    所以你的 100 条数据里，第三类必须占有明确的一份数量，并且要覆盖不同长度、不同错位位置：错在最前面（)(）、错在中间（())(）、错在偏后（(())())( 这类）、以及错好几处（)()(）。

    32.3　输出格式的精确要求：一个字符都不能差¶

    模型答完之后，平台会拿它的输出跟标准答案比对。比对方式题面写得非常直白：只去掉最终答案首尾的空白，然后逐字匹配，不改变内部的空格和大小写。这就意味着下面这些都会算错：

    模型输出 判定 原因
    [Valid]: YES 对 完全符合
    [Valid]: YES 错 冒号后是两个空格，内部空格不可改
    [Valid]:YES 错 冒号后少了那一个半角空格
    [valid]: YES 错 大小写必须固定：V 大写
    [Valid]: Yes 错 YES 必须全大写
    序列合法，所以 [Valid]: YES 错 不许加解释；逐字匹配看的是整串
    [Valid]: NO，因为括号未闭合 错 多写了理由
    输出被平台 `` 之类包裹的一段话 错 本题关闭 thinking，直接输答案

    必背

    两种正确答案，背到能默写：合法是 [Valid]: YES，不合法是 [Valid]: NO。方括号、大写 V、冒号、冒号后恰好一个半角空格、三个字母全大写，一个都不能改，前后也不能多一个字。

    顺带解释两个词，这一部分以后会反复用到：

    • Token（词元）：模型不认识"字"，它把文本切成一小块一小块来读，每一小块叫一个 Token。中文通常一个字算一个 Token 左右，英文单词和标点也各占若干。[Valid]: YES 这样一行，大概要吃掉几个到十几个 Token。本题最多生成 128 Token，意思是模型最多能吐这么多块，用完就强制停；答案本身很短，正常绝不会超，但如果模型养成"先啰嗦一句再给答案"的习惯，就可能被截断，而截断就算错。

    • thinking（思考）：有些模型可以先在内部写一段"草稿"再给正式答案。本题关闭 thinking，模型必须直接给答案。好处是稳定、省 Token；代价是它没有任何"算一算"的机会，只能靠训练时养成的直觉。这就是为什么数据质量比参数更重要。

    32.4　三份提交物：train.jsonl、submission.py、training_params.json¶

    这一题要交的东西只有三份，但每一份都有硬性限制。限制不是建议，是平台在训练前会真的检查、不满足就报错的门槛。

    文件 要写什么 限制
    train.jsonl 你自己构造并标注的原始数据，UTF-8 编码，每行一个 JSON 对象，字段是 sequence 与 valid，两个都必须是字符串 1 至 100 条；处理后也要保持在 1 至 100 条；整个文件最多 256KiB；每条数据连同固定系统提示词、对话格式和正确答案最多 512 Token；超长或空数据在训练前报错，平台不会截断正确答案
    submission.py 实现 process_data(records)：把已经标注好的原始记录整理成标准格式 代码最多 16KiB；只允许纯函数定义、文档字符串，以及 json、re、collections 标准库；常量写在函数内；不读文件、不联网、不调模型
    training_params.json 填五项训练参数 每项都必须在允许范围内；一个文件里只写这五个键

    一个常见的困惑："原始数据和处理后的数据均不超过 100 条"是什么意思？意思是：你写的 train.jsonl 不能超过 100 行，而经过 process_data 清洗之后剩下的行数也要在 1 到 100 之间。如果你的函数把大部分记录都判成"跳过"，清洗后只剩 0 条，训练就会因为"空数据"报错，一分也拿不到。

    三份文件之间还有一条隐含的"数据链"，理解它就不容易交错东西：train.jsonl 是原始素材，submission.py 是加工机器，加工出来的标准记录才是真正喂给模型的东西；training_params.json 决定用多大的力气去学。所以如果最终成绩不好，排查的入口永远在这条链的最上游——先看原始素材够不够全，再看加工机器有没有出错，最后才看力气是否合适。

    坑

    "每条最多 512 Token"这条限制不是让你去数 Token 数，而是提醒你别在 sequence 里塞奇怪的东西。本题的括号串最长 12 个字符，加上固定系统提示词（几十个 Token）和对话模板标记，正常情况下离 512 很远。真正会踩雷的是：你在 valid 字段里写上"YES，因为这个串..."这种解释，或者在数据里混入超长字符串。记住 valid 只能是 YES 或 NO。

    最后还有一句关于提交的重要规定：最终提交会锁定三份作答文件以及对应的训练产物。公开四点（训练后现场可见）和隐藏四点（考后统一评测）必须用同一个最终 LoRA，不允许"把不同训练版本里各自最高的那一个拼起来"。也就是说，你没有"用 A 版本跑公开点、用 B 版本跑隐藏点"这条路。你训练出来的那一个模型，一荣俱荣。

    32.5　评分结构：函数 2 点 20 分、公开模型 4 点 40 分、隐藏模型 4 点 40 分¶

    第二题满分 100 分，拆成三块。这三块的反馈方式和作答时序完全不同，必须分清楚，否则你会把时间花在错误的地方。

    评测部分 点数与分值 反馈方式
    数据处理函数 2 点，每点 10 分 共 20 分 训练前就能运行；完整展示输入、期望返回值、实际返回值和对错
    训练后模型：公开 4 点，每点 10 分 共 40 分 训练完成、保存并重载 LoRA 之后运行；完整展示输入、标准答案、模型输出和对错
    训练后模型：隐藏 4 点，每点 10 分 共 40 分 考试结束后统一运行；现场不展示输入、答案、输出或分数

    把这张表翻译成作战计划：

    • 20 分是"白给"的。函数点在你训练之前就能反复验证，输入和期望全部公开，属于完全可以拿到手的分。先把这 20 分稳稳拿住，再去折腾训练。

    • 40 分是"看得见但不够"的。公开四点在训练后能看到反馈，但它只覆盖了题目规则的一部分；它全对，不代表隐藏四点全对。

    • 40 分是"看不见的"。隐藏四点考的正是你有没有真的把规律覆盖全——尤其是"数量相等但顺序错"这一类的不同长度变体。

    考试怎么考

    模型点的判定细节：每个模型点只生成一次（不是三次取多数）；推理关闭 thinking、使用确定性生成、最多生成 128 Token；比对时只去掉答案首尾空白后逐字匹配，内部空格和大小写都不改。还有一个善意的规定：平台训练故障单独标记，不当成模型答错——如果你确定是平台侧的问题，分数不会被冤枉扣掉。

    技巧

    现场可见部分最多 60 分（函数 20 分加公开模型 40 分）。这意味着你在考场上"看到的分数"最多只有六成，剩下四成完全没有反馈。所以千万不要用"公开四点全对"当作收工信号，而要反过来问自己：我构造的数据，是否让模型在没见过的长度和没见过的错位位置上也只依赖那两条正确规则？

    本章要记住的 6 件事

    • 输入 = 全角冒号的 序列： 加上 2 至 12 个半角圆括号；前缀里没有空格。
    • 合法要同时满足两条：任意前缀左括号不少于右括号，且左右总数相等。
    • 不合法分四类：未闭合、额外右括号、数量相等但顺序错、奇数长度；第三类最容易漏，也最容易被隐藏点考到。
    • 答案只有两种写法：[Valid]: YES 与 [Valid]: NO，冒号后恰好一个半角空格，大小写固定，不加解释。
    • 三份提交物是 train.jsonl（1～100 条、≤256KiB、单条≤512 Token）、submission.py（≤16KiB、纯函数 + json/re/collections）、training_params.json（五项参数）。
    • 分数结构是函数 2 点 20 分、公开模型 4 点 40 分、隐藏模型 4 点 40 分；推理关 thinking、确定性生成、最多 128 Token、逐字匹配。

    本章目标

    读完这一章，你能逐条背出官方六条清洗规则，说清每条规则"在防什么错"，并且明白为什么这个函数不许判断合法性。

    这一章不写完整代码（完整实现在第 20 章），只做一件事：把官方给的数据清洗规则拆成六条，一条一条讲清楚它要你做什么、容易在哪里做错。规则是官方原文的意思，不要自己发挥。

    32.6　总览：六条规则一张表¶

    序号 规则要点 做错会怎样
    1 records 不是列表 → 抛 ValueError；不是字典、缺少 sequence/valid、字段类型不符 → 跳过；只看这两个字段 该抛的没抛，函数点直接错；该跳的没跳，脏数据进训练
    2 删除 sequence 全部空白，处理后长度必须 2～12 且只含半角括号，否则跳过整条 把 (a)、空串放进训练，或把合法串误杀
    3 valid 去首尾空白转大写，只接受 YES/NO；input 为 序列：加规范化串，output 为 [Valid]:加标签 标签大小写错、前缀冒号写错、答案少一个空格
    4 按规范化后的 input 稳定去重；同 input 不同 output 抛 ValueError 顺序被打乱、冲突标签被悄悄丢掉
    5 返回列表；不打印；不扩增；不调模型/网络/文件；不判断合法性 输出多了调试信息、数据被自己造出来、标签被函数改了
    6 代码 ≤16KiB；只用纯函数定义、文档字符串和 json/re/collections；常量写在函数内 函数点因为不合规被判错

    32.7　规则 1：records 必须是列表，脏记录要跳过¶

    原文：records 不是列表时，抛出 ValueError。按原始顺序处理；不是字典、缺少 sequence/valid 或字段类型不符合的记录，跳过。只读取这两个规定字段，其他字段忽略。

    这条规则有三个动作，注意它们不是同一种处理：

    • 抛异常：records 本身不是列表（比如传进来一个字符串、一个数字、None）→ 抛 ValueError。这是"整批输入不可用"，要立刻报错。

    • 跳过：列表里某一条有问题 → 安静地跳过它，继续处理后面的。包括：这一项不是字典（例如公开点 P02 里的 null）、缺少 sequence 或 valid、字段存在但不是字符串（比如 valid 是数字 1，或 sequence 是 None）。

    • 忽略：记录里除了这两个字段还有别的键 → 完全不管，不读、不抄、不报错。

    坑

    公开函数测试点 P02 的第一项就是 null。它在 JSON 里表示"空"，在 Python 里是 None。它既不是字典，也不是字符。很多同学写 record.get("sequence") 之前忘了判断类型，程序直接崩，这一整点 10 分就没了。正确姿势是先 isinstance(record, dict) 再取值。isinstance 是 Python 内置函数，用来问"这个东西是不是某种类型"。

    32.8　规则 2：删空白、长度 2～12、只允许半角括号¶

    原文：删除 sequence 中的全部空白字符。处理后长度必须为 2 至 12，而且只能包含半角 ( 和 )，否则跳过整条记录。这里只做字符和长度检查，不判断括号是否合法。

    三个细节必须抠清楚：

    • "全部"空白，不是"首尾"空白。 ( )(()) 要变成 ()(())，中间的空白也要删。( ( ) ) 要变成 (())。空白包括半角空格、制表符、换行符，以及全角空格 。用正则 re.sub(r"\s+", "", sequence) 一次搞定。

    • 长度是"删除空白之后"的长度，不是原始长度。( ( ) ) 原始长度 9，删完长度 4，在范围内，应该保留。

    • "只做字符和长度检查"：)()( 字符合法、长度 4 合法，所以它要被保留。函数不许因为"它不合法"就把它删掉——它的标签是 NO，正好是训练要的反例。同理 (((( 也要保留。

    必背

    这一章最容易混的两个词：格式合法（格式检查）指"长度 2～12 且只有半角括号"；序列合法（逻辑判断）指"过程条件 + 结束条件都满足"。process_data 只管第一个，绝不许管第二个。

    技巧

    用一条正则同时管长度和字符：^[()]{2,12}$。它要求整串从开头到结尾由 2 到 12 个 ( 或 ) 组成，多一个字符都不行。写正则时记住 {2,12} 里的数字是闭区间，长度 2 和长度 12 都算合格。

    32.9　规则 3：valid 归一化与 input/output 的精确拼接¶

    原文：valid 去掉首尾空白并转为大写，只接受 YES 或 NO；否则跳过整条记录。input 为"序列："加规范化后的括号串；output 为"[Valid]: "加已有标签。

    这里要区分两种不同的空白处理，它们是故意的：

    字段 空白怎么处理 为什么不一样
    sequence 删除全部空白 括号串里的空格是录入噪音，删掉才能统一比对
    valid 只去掉首尾空白 标签本身不该有内部空格；去首尾是为了容忍 " yes " 这种写法

    转大写是为了容忍 "yes"、"Yes"、" no " 这些手写变体。但容忍是有限的：转完大写之后，必须正好等于 "YES" 或 "NO"。所以公开点 P02 里 "MAYBE" 会被跳过——它不是 YES 也不是 NO。

    坑

    拼接 input 和 output 时最容易出三个错：一是前缀里的冒号打成半角（题目要全角 ：）；二是 output 里冒号后忘了那个半角空格（题目要 [Valid]: 带一个空格）；三是在输出里用 label.upper() 之外还要加引号或括号。正确结果长这样：{"input": "序列：()(())", "output": "[Valid]: YES"}。建议把这两段前缀作为常量写在函数内部（规则 6 也要求常量写在函数内），只写一次，避免两处不一致。

    32.10　规则 4：按规范化后的 input 稳定去重，冲突要抛错¶

    原文：按规范化后的 input 稳定去重。同一 input 和同一 output 只保留首次出现；同一 input 对应不同 output 时，抛出 ValueError，不能悄悄选一个标签。

    这句话里有三个关键字，都要抠：

    • 按规范化后的 input：判断两条记录是不是"重复"，看的是清洗之后的 input，不是原始 sequence。所以 " ( ( ) ) " 和 "(())" 会被认定成同一条，后者被丢掉。这正是公开点 P02 的情况。

    • 稳定：稳定去重的意思是"保留首次出现的那一条，并且保住所有记录原有的先后顺序"。所以不能用集合（set）来去重——集合会把顺序打乱。要用能记住插入顺序的字典，比如 collections.OrderedDict，或者直接用 Python 3.7 之后本来就保序的普通字典。

    • 冲突抛 ValueError：同一个 input，第一次标签是 YES，第二次标签是 NO——这时不许挑一个留下，而要抛 ValueError。因为这说明"你的标签自相矛盾"，函数没法替你决定谁对。注意：同一 input 同一 output 只是普通重复，跳过即可，不抛错。

    考试怎么考

    去重是 P02 拿分的关键。P02 期望只返回一条，就是因为 " ( ( ) ) " 和 "(())" 规范化之后是同一个 input。如果你只按原始字符串去重，会返回两条，这个点就错了。同时，顺序也在评分范围内：返回列表要按原始顺序排列，一条都不能错位。

    32.11　规则 5：只清洗，不判断，不打印，不扩增¶

    原文：返回列表，不打印答案，不扩增数据。不调用模型、网络或外部服务，不读取文件或评测数据，不用匹配算法补写标签。

    这条规则是整道题的"心理测试"：它逼你放弃"顺手帮模型判断一下合法性"的冲动。逐条翻译成人话：

    禁止事项 为什么被禁止 违规后果
    判断合法性、改标签 标签是要考你的部分；函数替你判，等于作弊 函数点判错，数据标签也不再是你自己的
    补写标签、用匹配算法猜 同上，且会引入不可控的错标 同上
    扩增数据（自动造新样本） 数据构造是你的任务，函数只负责整理 处理后条数可能超过 100，训练前报错
    打印输出 评测程序按返回值判断，打印会污染输出 轻则日志混乱，重则判错
    读文件、读评测数据、联网、调模型 评测环境不保证可用，也属于作弊 直接违规

    坑

    调试时顺手写的 print 最容易忘删。养成习惯：提交前在文件里搜一遍 print，确保一个都没有。同理，函数必须 return 一个列表，不是打印、也不是返回字典。

    32.12　规则 6：纯函数、允许的标准库、常量位置与 16KiB 上限¶

    原文：函数代码最多 16KiB，只使用纯函数定义、文档字符串及 json、re、collections 标准库；常量写在函数内。

    逐项解释：

    • 纯函数定义：文件里主要是 def 出来的函数（本例就是 process_data），加上必要的 import。不要写顶层执行的代码、不要写类和全局变量。

    • 文档字符串：函数里那对三引号包起来的说明文字是允许的，写清楚用途是好习惯。

    • 只允许 json、re、collections 三个标准库：不要 import os、import sys、import random，更不要第三方库。本题其实只需要 re（删空白、校验格式）和 collections（稳定去重用的 OrderedDict）；json 在允许清单里，但这个函数用不到。如果打算手动读 train.jsonl，那是 NO，规则 5 明确禁止读文件。

    • 常量写在函数内：像 "序列："、"[Valid]: "、r"^[()]{2,12}$" 这类常量，定义在函数体里面，不要提到模块顶层。

    • 代码最多 16KiB：这是文件体积上限，不是行数。本题实现大概三十行，远低于上限；但如果你复制了一堆无用代码或超长注释，也要留意。

    技巧

    把"允许的清单"当白名单来用：写每一行之前问一句"这行是纯函数定义、文档字符串，还是 json/re/collections？"如果都不是，就别写。这套自查能让你避开绝大多数函数点的失分。

    本章要记住的 6 件事

    • 不是列表抛 ValueError；列表里的坏记录（非字典、缺字段、类型不符）跳过；其他字段忽略。
    • sequence 删全部空白，长度必须 2～12 且只含半角括号，否则跳过；这里不判断括号是否合法。
    • valid 只去首尾空白并转大写，只接受 YES/NO；input = "序列：" + 规范化串，output = "[Valid]: " + 标签（全角冒号、半角冒号加一个空格）。
    • 按 input 稳定去重：同 input 同 output 保留首次出现；同 input 不同 output 抛 ValueError。
    • 返回列表，不打印、不扩增、不判断合法性、不读文件不联网。
    • 代码 ≤16KiB，只用纯函数、文档字符串和 json/re/collections，常量写在函数内。
